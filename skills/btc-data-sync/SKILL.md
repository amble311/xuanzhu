# 行情数据检查与同步

数据链是「交易所公开接口 → 本地行情库（`<模式目录>/data/btc.db`）→ 指标/信号/回测」。
只有**本地库**被计算层使用，所以数据不新鲜时一切结论都不可信。

平台口径（端点、市场类型、符号、分页限频、成本）见
`references/exchange-binance.md`，换平台时这份文件跟着换。
拉数据一律用 `btc_sync`，不要用 `bash` 手拼 HTTP —— 代理、分页去重与错误归类都在代码里。

> 数据通常已由**常驻后端**在巡检时自动更新（巡检间隔由模型决定，不是固定值），
> 所以先 `btc_status` 看，确实落后再手动 `btc_sync`。后端本身用
> `xzh btc status` / `xzh btc stop` 管理，不要在对话里用 `bash` 去 kill 进程。

## 检查（先看再补）

`btc_status` 返回：

| 字段 | 判读 |
|---|---|
| `timeframes.1d.bars` | 日线根数与最新时间；少于 200 根时回测/信号会直接报数据不足 |
| `timeframes.1h.bars` | 小时线；少于 120 根时 1h 择时会 `degraded=true`（4h 判势需要更多） |
| `timeframes.*.last_utc` | 与当前时间差超过 2 天（日线）就该同步 |
| `db_path` | 本地库位置，排查「同步了但没生效」时看它对不对 |

## 同步

`btc_sync`（增量：从库内最后一根之后开始拉，不会重复写）

- 默认 `timeframe=all`（日线 + 小时线）；只缺一个时传 `1d` / `1h`；
- `days` 控制回补上限：日线默认 750 天、小时线默认 60 天；
- 首次全量大约 750 根日线 + 1440 根小时线，几秒内完成。

同步完成后**重新 `btc_status` 确认根数与最新时间都前进了**，不要只看工具说"写入 N 根"。

## 排查

| 现象 | 处理 |
|---|---|
| 拉取报 HTTP / 超时 | 大陆网络需代理：先 `xzh vpn` 配好再同步（xzh 的请求会走同一个代理） |
| 报「计算环境未安装」 | 首次进入模式会自动准备；若当时联网失败，退出后运行 `xzh btc setup` 重试（损坏用 `--force`） |
| 写入成功但根数没变 | 看 `db_path` 是否与刚才写的库一致；`XZH_BTC_HOME` 改过就会写到别处 |
| 只差最近 1 根 | 正常：当日 K 线未收盘时币安给的是进行中的那根，不必强补 |

## 禁止

- 不要 `rm` 行情库、也不要手工改库里的表来"修数据"——重建要走同步；
- 不要为了让回测数字好看而调整数据窗口（那是改口径，不是修数据）。
