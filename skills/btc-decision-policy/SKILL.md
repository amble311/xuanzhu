# 决策指令（对话如何影响后台判断）

后台巡检是**独立进程、独立轮次**，不共享当前对话的上下文。用户在对话里说
「以后别逆势，单笔最多 1%」，如果只回一句「记住了」，下一轮巡检根本不知道。

所以长期要求必须落盘：`btc_policy` 写 `<模式目录>/policy.md`，每轮巡检都会把全文
注入提示词（放在末尾，并在开头声明「优先级高于你的个人偏好，低于资金安全」）。

## 什么时候写

- 用户表达**长期偏好**：风控阈值（单笔 ≤1%、最大回撤 20%）、周期偏好（只看日线）、
  禁止的动作（不逆势、不加仓、不做空）；
- 用户纠正你的判断方式：「不要每次都跑回测」「别在震荡市做」；
- 用户给出可验证的纪律：同一自然日最多一次、止损后当日不再入场。

**不要**把一次性要求写进去（「这次先别买」是当前决策，不是长期规则），
也不要写无法验证的偏好（「保守一点」→ 改成「单笔风险 ≤1%」）。

## 怎么用

| 目的 | 调用 |
| --- | --- |
| 追加一条 | `btc_policy {action: "append", content: "单笔风险不超过账户 1%"}` |
| 整份替换 | `btc_policy {action: "replace", content: "..."}`（用户重写整套策略时） |
| 查看 | `btc_policy {action: "show"}` |
| 清空 | `btc_policy {action: "clear"}`（仅用户明确要求，并复述会失效哪些约束） |

## 写法要求

- **具体、可验证**：给阈值 / 周期 / 明确的禁用动作，不写形容词；
- **一条一件事**，便于之后单独撤销；
- **不与资金安全冲突**：像「满仓干」这种要求必须拒绝并说明风险；
- 上限 4000 字符，超出会丢最旧的条目 —— 定期把同类要求合并成一条。

## 与其它机制的区别

| 机制 | 存什么 | 谁读 |
| --- | --- | --- |
| `btc_policy` | 以后怎么做（约束） | 每轮巡检的提示词 |
| `memory_write` | 发生过什么（结论） | 下次对话 / 巡检的项目记忆 |
| `btc_schedule` | 下次什么时候看（时间） | 后端定时器 |
| `btc_backtest` | 参数是否有效（证据） | 当前对话 |

用户说「记住：以后只做多」→ policy；用户问「上次那笔为什么亏」→ memory。

## 确认

写完要告诉用户**具体新增了哪条**（工具返回里带全文），不要只说「已记录」。
